# Notes

## Задача 1

Исправил порядок координат в `distanceKm`: у филиала передавались `lon` и `lat` вместо `lat` и `lon`.

Добавил правила `pickup_point` и `city`, выбор ближайшего филиала внутри города и ограничение 42 км (`too_far`). Лимит считается по дате `createdAt` в UTC+5. Если филиал, выбранный правилом `single`, `pickup_point`, `city` или `geo`, заполнен, ищу ближайший свободный филиал магазина; `manual` лимит не проверяет.

В API добавил `POST /orders/:id/assign` (повторный вызов возвращает сохранённое распределение) и `GET /branches/:id/load?date=...` с проверкой даты. Тесты на новые правила и лимит добавил в `task-1-dispatch/test/router.test.ts`.

Допущения:

- заказ, распределённый вручную, учитывается в загрузке филиала, хотя лимит для него не проверяется;
- при заполненном филиале запасной ищется по всем активным филиалам магазина, а не только по городу заказа;
- если ближайший свободный филиал дальше 42 км, возвращается `too_far`.

Если экземпляров несколько и общая БД:

- хранить распределения в таблице с уникальным `order_id`, чтобы повторный запрос не создавал второе распределение;
- загрузку считать в транзакции: `SELECT ... FOR UPDATE` по строке филиала или атомарный `UPDATE` с условием `assigned < daily_limit`;
- при конфликте уникального индекса возвращать уже сохранённое распределение;
- дату считать на стороне приложения в UTC+5 или хранить отдельным полем `load_date`.

## Задача 2

Исправил `overlaps`: интервалы, которые касаются границами, больше не считаются пересекающимися.

Дописал `getSlots`: учитываются рабочий день, перерывы, активные записи мастера и текущее время. После каждой активной записи добавил 7 минут на уборку. Отменённые записи не блокируют слоты. В API добавил `GET /masters/:id/slots`, `POST /bookings` и `DELETE /bookings/:id`. Телефон привожу к `+77012345678`, принимаю `8...`, `+7...` и номер без кода страны.

Одновременные бронирования в одном процессе решаю очередью: проверка слота и вставка выполняются последовательно, поэтому второй запрос получает `409 slot_unavailable`. На это есть тест.

Допущения:

- 7 минут добавляются после любой активной записи мастера, независимо от услуги;
- слот должен начинаться строго позже текущего времени;
- запись с ненулевыми секундами или миллисекундами не считается попаданием в слот.

Если экземпляров несколько и PostgreSQL:

- хранить записи в таблице с `tstzrange` и exclusion constraint по `master_id` и пересечению интервалов для активных записей;
- создавать запись в транзакции `SERIALIZABLE` или под advisory lock по `master_id`;
- обрабатывать конфликт ограничения и возвращать `409`;
- добавить idempotency key, чтобы повторный POST не создавал дубль.
